# RevenueOps 可复现评估 v1

目标：分别证明计算、证据、拒答、可用性和效率，不用一个综合分替代五种证据。当前只建立基线，不宣称产品已通过商业验证。

## 1. 执行与复现

在仓库根目录、已安装项目 API 依赖的 Python 环境运行：

```powershell
python scripts/evaluate_product.py --report data/processed/evaluation-baseline.json
python tests/test_product_evaluation.py
```

第一个命令退出码：0=自动验收全通过；1=发现产品缺口；2=评估运行错误。第二个命令验证评估器本身。不能用评估器单元测试通过来替代产品验收通过。

评估不调用模型、不发邮件、不读真实订单或客户数据。SQL 使用内存数据库；草案接口使用模拟身份、合成汇总和临时文件，禁止网络连接。模拟身份只用于隔离评估，**不构成认证或权限验收**。报告包含源码 SHA-256、Git 版本、Python 版本和逐项结果；本地报告位于 git 忽略的数据目录。无需新增依赖。

| 要证明什么 | 当前验证 | 验收条件 | 尚未覆盖 |
|---|---|---|---|
| 指标算得对 | SQLite 独立计算 + 手算锚点 | 按生产输出精度逐字段一致，拒绝非有限金额和非整数人数 | 所有业务口径及模型输出 |
| 建议有依据 | 信号数值核对；实际草案 API；伪造引用负例 | 数字可核对；草案保存可重建来源；无依据内容不计作已核实 | 在线 LLM 多次输出、每条自然语言结论 |
| 数据不足不会乱说 | 开发店、小样本、短历史、缺日期、缺金额、截断数据 | 不将不完整输入标为 ready 或生成误导信号；极小实验须提示限制 | 更多异常组合、统计功效 |
| 用户理解和操作 | 下述真人任务协议 | 任务完成率至少 80%，关键误解为 0 | 尚未邀请或测试真人 |
| 比原方法有帮助 | 下述配对比较协议 | 时间中位数改善至少 20%，错误不增加 | 尚无实测数据 |

上述真人阈值是试点前暂定门槛，不是行业标准，不得见到结果后临时降低。

## 2. 合成数据与口径

实验锚点：处理组 100 人、20 个购买用户、收入 2000；对照组 100 人、10 个购买用户、收入 1000；成本 200。同一币种、同一归因窗口。

手算：20% 对 10%；提升 10 个百分点，相对提升 100%；增量订单估计 10；对照客单价 100；增量收入估计 1000；收入口径 ROI=(1000−200)/200=4。

生产估计器使用“转化率差 × 处理组人数 × 对照客单价”，不是两组收入直接相减。因此仅改变处理组收入不改变估计结果，这项通过只证明实现与既定公式一致。订单数必须代表购买用户数或满足每人至多一单的假设，否则不能解释成用户转化率。收入 ROI 不是扣除货品、履约等成本后的利润 ROI；退款口径、随机分组、同窗口及混杂因素仍需审核。对照组零订单时代码返回零收入估计，不能解释为已证明零增量。

信号数据：2026-09-01 至 09-14，每日 2 单、毛额 120；前 7 天每日净额 100，后 7 天每日净额 60；退款调整为毛额减净额。独立 SQL 预期：前期 700、近期 420、毛额 1680、调整 560。全部为虚构汇总，不代表任何商家。

测试覆盖正提升、负提升、不等组、零成本、零对照订单、小数金额。金额输出按两位小数、转化率等按既定精度比较，绝对容差 1e-8；不将缺字段、NaN 或无穷大当作零。

## 3. 2026-10-02 实际基线

22 项：14 通过、8 未通过、0 运行错误。自动检查通过比例不是“产品完成度”，也不是准确率估计。

| 未通过用例 | 实测问题 | 修复验收方向 |
|---|---|---|
| nonfinite_revenue | NaN 收入被接受 | 明确拒绝非有限金额 |
| fractional_users | 小数人数被接受 | 人数和购买人数必须是整数 |
| draft_evidence_link | 草案保存了信号 ID，但没有数值证据快照 | 保存指标、窗口、币种和来源版本；与原信号核对 |
| fabricated_citation_not_credited | 无工具结果的伪造引用仍获得结构分 | 区分结构完整性和事实验证，不把前者展示成可信度 |
| truncated_history | 截断数据仍 ready 且生成两个信号 | 阻止完整性依赖的结论或明确降级 |
| missing_dates | 三个空日期记录仍 ready | 校验日期内容和有效覆盖范围 |
| missing_net_sales | 后七天缺金额被当作零并生成信号 | 缺失值不等于零，缺关键字段拒绝分析 |
| small_experiment_warning | 每组两人也输出无样本限制的结果 | 可计算描述值，但必须说明不能推断可靠增量 |

以上保留首次评估时的失败记录。初版报告为 `data/processed/evaluation-baseline.json`；初版草案用例失败在第一个信号，不表示全部草案分支均已覆盖。

### 修复后复验（2026-10-02）

原 22 项验收全部通过，修复后报告单独保存至 `data/processed/evaluation-fixed.json`，初版失败报告保留。新增回归测试位于 `tests/test_evaluation_fixes.py`，覆盖非法数值、API 不截断人数、同步源金额缺失、重复/无效日期、汇总不一致、引用伪造、两类草案落盘及截断数据禁止创建草案。

修复后行为：有限非负金额、整数人数/订单在共享计算器校验，接口原样传入以避免截断；不完整趋势返回 insufficient_data；Shopify 源金额解析不再将缺失或无效值改成零；草案保存数值、期间、币种及汇总指纹。任一组少于 30 人会附描述性结果警告，并在复盘页面显示。30 人只是提示阈值，不是统计功效保证；任何结果均附显著性未检验及收入 ROI 的限制。

证据评分版本升级为 qa_v2：source 必须对应当前成功工具结果；evidence 使用 `{ "path": "0.total_sales", "value": 123.45, "label": "销售额" }`，逐项匹配实际 data 字段才获得 evidence_coverage。文本非空率单独记录为 structural_evidence_coverage。quality_score 只衡量字段引用匹配和行动完整性，**不验证标题语义、推导结论或因果关系**；不能展示为“AI 正确率”。在线模型和真人两类评估仍待执行。

## 4. 真正的 AI 输出评估（待执行）

本轮没有运行在线模型，所以不能证明“AI 不会幻觉”。用上面的合成汇总建立固定题单：计算两组提升、说明近期下降依据、缺净额时能否分析、两人实验能否扩大投放。输入中明确日期、币种和退款口径。

每次留存模型/版本、提示词哈希、输入哈希、温度、运行时间及重复编号；每题至少独立重复三次。只用合成数据，模型调用费用需单独确认。逐条拆分可核验主张，记录引用字段、期间、计算表达式、SQL 参考值、实际值和通过/失败。没有来源的数字或因果承诺计失败；必要的拒答不能算任务失败。不得只检查引用字符串非空。

允许结论：有明确证据的描述、带假设的估计、缺失时请求最小补充信息。禁止结论：小样本保证增长、把样本场景当真实店铺、把收入 ROI 当利润或已证实因果效果。

## 5. 真人任务与配对对照（待执行）

邀请 3–5 位有电商运营经验、知情同意的参与者。以匿名编号记录，不保存姓名、客户名单或商家原始数据。未获许可不录屏。学生或开发者自测可做排障，不能替代目标用户结果。

四项任务，每项最多 10 分钟：

1. 找出两周净销售变化，并展示具体证据和日期。
2. 面对缺金额或历史截断，判断能否继续分析并说明原因。
3. 从信号创建一份待人工审批的行动草案，解释依据；不实际发送活动。
4. 解释实验增量和 ROI，并说出不能据此保证盈利的限制。

同一参与者分别使用其熟悉的原方法（表格/SQL/人工）和 RevenueOps 完成相同目标。使用难度一致、数值不同的合成 A/B 数据避免记答案；轮换先后顺序（AB/BA），保留输入版本及参考答案。不在计时中教学；提示、卡点、失败都记录。

记录到 `evaluation-operator-records.csv`，每种方法每任务一行。时间从展示任务到提交答案；超时记 600 秒、完成=0；失败不能从效率比较中删除。错误分为数值、来源、关键业务误解；人工修改分“字段数”和“文本修改次数”，不要混成一个模糊分数。由不知道使用方法的复核者按参考答案判定；意见分歧记录后裁定。

对每个参与者/任务配对计算节省率=(原方法耗时−产品耗时)/原方法耗时，再报告中位数、范围、配对数及两种方法完成率；同时比较错误、协助和修改量，不以单个成功案例作结论。小样本结果仅用于迭代，不宣称统计显著。

闭环顺序：修复自动验收失败 → 全量重跑留版本证据 → 真人任务 → 配对对照 → 商家决定是否愿意继续或付费。自营测试、演示成功、自动测试通过都不等于外部付费需求成立。
